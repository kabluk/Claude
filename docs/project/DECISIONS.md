## D-024 · 2026-08-06 · accepted
Владелец явно одобрил Resend для трёх узлов разом (не общее «ОК на внешние
сервисы» — по AskUserQuestion выбраны конкретно `A2-LEAD-EMAIL`,
`A2-CLAIM-EMAIL`, `A2-OUTREACH-SEND`; правило проекта про раздельное одобрение
per-node зафиксировано, а не молча предположено). Реальный `RESEND_API_KEY`
получен и использован только в памяти процесса (как и Cloudflare/Anthropic
ключи ранее, D-020/D-021) — не записан на диск, не закоммичен.

Живая проверка ключа вскрыла два факта, требующих зафиксировать здесь, а не
предполагать по коду:

1. **Ключ ограничен правом «только отправка»** (`GET /domains` → 401
   `restricted_api_key`) — не могу программно проверить, какие домены
   верифицированы. Это осознанное least-privilege владельца (D-014/
   devops-engineer.md уже требует такого масштаба доступа), не баг.
2. **Общий sandbox-домен Resend (`onboarding@resend.dev`) не может слать
   произвольным получателям** — подтверждено безопасным пробником на
   `test@example.com` (IANA-зарезервированный домен, письмо технически не
   могло уйти живому человеку): `422 validation_error, "Please use our
   testing email address instead of domains like example.com"`. Отправка на
   собственный email владельца (`zincroom@gmail.com`) при этом реально
   прошла (`200`, настоящий id письма). Вывод: пока не верифицирован
   собственный домен в Resend (которому нужен реальный домен сайта —
   A0-ORIGIN, который упирается в A0-OWNER-LEGAL), **ни один узел не может
   реально доставить письмо стороннему получателю** — тот же корневой
   блокер, что уже был найден для `A2-OUTREACH-SEND` (`domains/growth.md`),
   теперь подтверждён и для `A2-LEAD-EMAIL`/`A2-CLAIM-EMAIL`, причём не
   предположением, а прямым ответом Resend API.

**Дополнительно, отдельная находка при подготовке `A2-LEAD-EMAIL`**: у типа
`Agency` (`data/a11y/types.ts`) нет поля email вообще — каталог никогда не
собирал общий контактный email агентства (только `website`), это было
осознанно вне scope до Фазы 2. Значит «отправить лид 3–5 подходящим
агентствам» в буквальном виде НЕЧЕМ реализовать: нет адреса получателя для
произвольного совпавшего агентства. Решение: `A2-LEAD-EMAIL` **не
реализуется в этой итерации** — это не «todo, руки не дошли», а настоящий,
не предвиденный при разбиении Фазы 2 (D-022) пробел в модели данных,
требующий отдельного решения владельца (добавить email в agencies.json?
слать только claimed-агентствам, у которых есть claims.email? что-то
третье?) прежде чем писать код, который иначе пришлось бы либо выдумывать
(нарушая R1/data-дисциплину), либо не проверить, кому реально слать.
`A2-CLAIM-EMAIL` эту проблему не имеет: адрес — `claims.email`, введённый
самим заявителем при создании заявки, уже есть в D1.

## D-023 · 2026-08-06 · accepted
`claims` (`migrations/0004_claims.sql`, INTERFACES.md §4) получила отдельный
`token` столбец (`migrations/0006_claim_token.sql`), выходя за буквальный scope
узла `A2-CLAIM-API` (`worker/routes/claim.js`) — раскрыто явно, не тихо (прецедент:
`A1-LANDING`/`A2-LEAD-FORM` уже трогали файлы вне буквального scope, когда без
этого узел был бы недостижим/некорректен). Причина: контракт `POST /api/claim`
(INTERFACES.md §2) описывает вход как отображающийся в ДВЕ разные вещи —
verify-link (уходит только на email, отдельный узел `A2-CLAIM-EMAIL`) и `claimId`
(возвращается вызывающему немедленно, 201). Если verify-токен в ссылке = тот же
`id`, что возвращается как `claimId` прямо в ответе API, то вызывающий получает
"доказательство владения почтой" без перехода по ссылке — ровно то, что
email-верификация должна предотвращать (например: атакующий указывает чужой
рабочий email агентства в поле `email`, получает `claimId` в ответе и тут же
верифицирует заявку, ни разу не увидев письма). Черновик `claims` в INTERFACES.md
§4 не содержал `token` — не пропущено по невнимательности, инструкция узла явно
просила зафиксировать решение здесь, если решу делать иначе, чем "домен/токен не
проверяются на этом шаге". Альтернатива (переиспользовать `patch_json` под
`{token}`) отклонена — тот столбец зарезервирован под предложенные правки профиля
агентства (см. комментарий `0004_claims.sql`), смешение форматов сломало бы
`A2-CLAIM-REBUILD`. Последствия: `INTERFACES.md` §4 обновлена (см. отдельную
правку); `A2-CLAIM-API` пишет `token` в D1, но НЕ возвращает его в ответе;
будущий verify-эндпоинт (вероятно часть `A2-CLAIM-EMAIL`, у него `worker/routes/
claim.js` тоже в scope) должен принимать токен из ссылки, искать по нему
(`idx_claims_token`), не по `id`.

## D-022 · 2026-08-06 · accepted
Фаза 2 (Lead Marketplace) разбита в `GRAPH.yaml` на 13 узлов вместо 4 backlog-строк

`approval_required`: `true` только там, где узел либо создаёт НОВЫЙ внешний
платный аккаунт/ключ (Resend, Stripe), либо реально пишет живым третьим лицам
(агентствам), либо заводит новую регулярную автоматизацию, трогающую прод
(`A2-CLAIM-REBUILD` — ежедневный CI-ребилд+деплой). `false` — там, где узел
только пишет код/схему и использует уже одобренный `accessatlas-scans` D1
(консистентно с тем, как A1-REPORT/A1-COST/A1-MATCH были размечены `false`
относительно уже одобренного A1-SCAN). Последствия: `A2-LEAD-SCHEMA` и
`A2-LEAD-FORM` (technically независимые от оплаты примеры, названные владельцем)
запущены через `/task-loop` в той же итерации; `A2-LEAD-API`/`A2-CLAIM-API`/
`A2-STRIPE-WEBHOOK-CODE`/`A2-CLAIM-SCHEMA`/`A2-STRIPE-SCHEMA`/`A2-OUTREACH-PREP`
тоже `approval_required: false` и готовы к `/task-loop` в следующих итерациях без
дополнительного разрешения владельца; `A2-LEAD-EMAIL`/`A2-CLAIM-EMAIL`/
`A2-STRIPE-LIVE`/`A2-CLAIM-REBUILD`/`A2-OUTREACH-SEND` заблокированы до явного
одобрения владельца per-node (Resend и Stripe — отдельные одобрения, не одно
общее «внешние сервисы»).

## D-020 · 2026-08-06 · accepted
A1-EXPLAIN закрыт живой проверкой с реальным `ANTHROPIC_API_KEY` (владелец дал
отдельное одобрение, D-016 это специально требовал). Прогон вскрыл настоящий
баг, не гипотетический: Claude Haiku оборачивает JSON-ответ в markdown code
fence (` ```json ... ``` `) несмотря на явную инструкцию в промпте «ONLY a JSON
object, no other text» — `parseExplainResponse` падал на `JSON.parse` и каждый
cache-miss отдавал 502. Ни одна из прежних синтетических фикстур это не
покрывала (все — чистый JSON без фенса), баг был невидим ревью кода и юнит-
тестам до реального вызова API. Исправлено: `stripCodeFence()` снимает фенс
перед `JSON.parse`, а не переписан промпт ещё строже — поведение модели не
гарантировано форматированием промпта, парсер должен быть терпимее к нему.
Live-проверено на `wrangler dev --var` (без записи ключа в файл/коммит):
`image-alt` и `color-contrast` — реальные, разумные объяснения, 200; повторный
запрос того же `ruleId` — cache hit из KV (0.025s против 3.8s на промахе,
~150×); заведомо не axe-core ruleId — модель абстинирует пустым `explanation`,
эндпоинт корректно отдаёт 502 с понятной причиной (D-016, ожидаемое поведение,
не баг). Последствия: `explain.test.mjs` пополнен фикстурами с фенсом (в т.ч.
без языкового тега `json` и заведомо битый JSON внутри фенса) — реальный ответ
модели теперь часть тестового покрытия, не только идеальный JSON.

## D-019 · 2026-08-06 · accepted
Retention сканов — 90 дней с `created_at`, ежедневный Cron Trigger удаляет
просроченные записи целиком (`DELETE FROM scans WHERE created_at < cutoff`,

агентства, не настолько долго, чтобы копить ненужный риск. Последствия: если
владелец захочет более короткое/длинное окно или разное окно по статусу
(`error` можно чистить быстрее `done`) — поменять `RETENTION_DAYS`, миграция
не нужна (использует существующий `idx_scans_created_at`). Cron включается
только на реальном деплое — до тех пор просроченные записи технически не
удаляются, только код к этому готов (см. A1-RETENTION в GRAPH.yaml).

## D-017 · 2026-08-06 · accepted — уточняет D-006
A1-COST реализован (`src/lib/costEstimate.ts`, интегрирован в `ReportPage.tsx`).
D-006 предлагал вилку как «интерполяцию между двумя соседними price bands» —
первая же живая проверка (Playwright, фикстуры с ручным расчётом ожидаемых
значений) показала, что это даёт неинформативно широкие диапазоны: 1 незначительная
находка оценивалась в «€0–€10k» (весь budget+mid разом), что практически бесполезно
для пользователя. Пересмотрено: одна находка → один price band по effort-score
(дубль логики `worker/lib/score.js`: считаем различные `ruleId`, не инстансы,
severe-правила весят ×2), сам band уже является диапазоном («€3k–10k»&nbsp;—
не точка), это и есть «вилка» из D-006, просто не через две границы, а через
естественный диапазон одного бэнда.

Формат чисел приведён к уже существующей конвенции проекта (`taxonomies.json`
priceBands: `"€3k–10k"`, один символ валюты на диапазон, не по одному на границу)
— тоже поймано верификацией, не увидено бы при простом код-ревью.

5 сценариев проверены живьём (Playwright, реальные вычисленные значения сверены
с ручным расчётом по формуле): 0 находок → секция скрыта; 1 minor → budget
(«Under €3k»); 2 critical → premium («€10k–30k»); 5 serious → enterprise
(«€30k+»); 40 повторов ОДНОГО правила → mid, не enterprise (дедуп работает,
не даёт задваивающимся находкам искусственно взвинчивать оценку). Каждое
состояние — 0 нарушений axe-core. Дисклеймер «оценка, не оферта» + ссылка на
каталог для реальной цены — обязательны рядом (D-006), не факультативны.

  несуществующего правила — `parseExplainResponse` трактует пустой `explanation`
  как `null` (нет объяснения), не как ошибку парсинга.
- Rate-limit — 30/час на IP (`checkExplainRateLimit`, обобщённое ядро вместе со
  сканом в `ratelimit.js`, добавлены юнит-тесты, которых раньше не было вообще
  ни у одной из этих функций).

## D-010 · 2026-08-05 · accepted
A1-SCAN реализован (`worker/`, `wrangler.jsonc`, `migrations/0001_init.sql`) с

- `worker/` — plain ESM JS, не TypeScript: проект уже написан без TS-тулчейна для
  `scripts/*.mjs`, отдельный `tsconfig.worker.json` + `@cloudflare/workers-types`
  добавили бы toolchain-сложность без пропорциональной пользы для MVP.
- Верификация в этой сессии: routing/валидация/D1 read-write/KV rate-limit/`ctx.waitUntil`

  `page.goto()` — но упёрся в MITM-прокси песочницы (`/root/.ccr/README.md`),

  кода: у настоящего Cloudflare Browser Rendering в проде прямой выход в интернет.
