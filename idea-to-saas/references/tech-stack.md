# Tech Stack — комбинации 2025–2026, таблица выбора, обязательные сервисы

Материалы этапа 4. Правило номер один: **скорость итераций важнее элегантности**. Стек, на котором пользователь пишет быстро сегодня, побеждает "правильный" стек, который надо учить.

## 1. Стек по умолчанию (solo / команда 1–3)

Если нет веских причин отклоняться — предлагай это:

| Слой | Выбор | Почему |
|---|---|---|
| Фреймворк | Next.js (App Router, TypeScript) | Фронт + API в одном репо, деплой в один пуш |
| БД | Supabase (Postgres) или Neon | Postgres, free tier, RLS из коробки (Supabase), branching БД (Neon) |
| Auth | Clerk или Supabase Auth | Готовые UI-компоненты, orgs/teams из коробки у Clerk |
| Платежи | Stripe (Checkout + Billing + webhooks) | Стандарт; не строй свои формы карт — только Checkout |
| Email | Resend + react-email | Транзакционные письма за час работы |
| Хостинг | Vercel | Превью на каждый PR, zero-config |
| Ошибки | Sentry | Free tier хватает MVP надолго |
| Аналитика | PostHog | События + funnels + session replay в одном, free tier |
| ORM | Drizzle или Prisma | Drizzle легче и ближе к SQL; Prisma — если уже знаком |

Стоимость до первых клиентов: $0–20/мес (почти всё — free tier). Единственный обязательный расход — домен.

### Альтернативы по ситуации

- **Пользователь силён в Rails / Laravel / Django** — бери его инструмент + Postgres + Stripe + хостинг Render/Fly/Railway. Rails с Hotwire или Django с HTMX закрывают 95% SaaS-UI без SPA. Это не "устаревший" выбор — это самый быстрый выбор для этого человека.
- **Тяжёлая фоновая обработка / AI-пайплайны** — Next.js для фронта + отдельный маленький Python-сервис (FastAPI) на Railway/Fly только для этой задачи. Это ещё не микросервисы — это один вспомогательный процесс.
- **Десктопоподобный интерактив (редакторы, канвасы)** — Vite + React SPA + отдельный API (Hono/Fastify) или Supabase напрямую.
- **B2B enterprise с первого дня (SSO/SAML)** — Clerk или WorkOS; не пиши SAML сам никогда.

### Чего не делать на MVP

- Микросервисы, Kubernetes, Terraform, отдельный кластер очередей — нет.
- Своя auth (пароли, сессии, reset-флоу) — нет, это недели работы и дыры в безопасности.
- Свой билинг поверх голого Stripe API вместо Checkout/Billing — нет.
- Монорепо-тулинг (Nx, Turborepo) для одного приложения — нет.
- NoSQL как основная БД "потому что гибко" — нет, бери Postgres, JSONB покроет гибкость.

## 2. Monolith first

- Одно приложение, одна БД, один деплой. Фоновые задачи — сначала как cron (Vercel Cron / Supabase pg_cron) или Inngest/Trigger.dev, а не как отдельный воркер-сервис.
- Выноси код в модули внутри монолита (папки `modules/billing`, `modules/projects`) — если когда-нибудь придётся выделять сервис, границы уже будут. Но не выделяй заранее.
- Сигналы, что монолита стало мало (до них — не трогай): деплой одной части ломает другую И это происходит регулярно; часть нагрузки требует другого масштабирования И метрики это показывают. "Мы вырастем и тогда..." — не сигнал.

## 3. Multi-tenancy basics (для B2B — с первого дня)

Переделка single-tenant → multi-tenant после запуска — недели боли. Если продукт хоть когда-нибудь продастся команде/компании:

1. Заведи таблицы `organizations` и `memberships` (user ↔ org, роль) с первого дня, даже если UI для команд появится потом.
2. Каждая бизнес-таблица получает `org_id NOT NULL REFERENCES organizations` + индекс. Все запросы фильтруются по `org_id` — без исключений.
3. Включи Postgres Row Level Security на каждой таблице с `org_id`: политика `org_id = current_org()`. RLS — страховка от самой стыдной ошибки SaaS: показать данные чужого клиента.
4. Clerk Organizations или Supabase Auth + своя `memberships` — оба варианта рабочие; Clerk даёт готовый UI приглашений.
5. Billing вешай на организацию, не на пользователя (`org_id` в Stripe customer metadata).

Схема "отдельная БД на клиента" — не для MVP; shared-БД с `org_id` + RLS достаточно до сотен клиентов.

## 4. Обязательные сервисы — чеклист

Перед этапом 5 у каждого пункта должен быть выбранный сервис (пустых строк не оставлять):

| Категория | Дефолт | Заметка |
|---|---|---|
| Auth | Clerk / Supabase Auth | + OAuth Google с первого дня, это удваивает конверсию регистрации |
| Payments | Stripe | Checkout, не кастомные формы; webhook `checkout.session.completed` обрабатывается идемпотентно |
| Transactional email | Resend | Welcome, reset, receipt; настрой SPF/DKIM на домене сразу |
| Error tracking | Sentry | Подключи и фронт, и сервер; alerts в личный канал |
| Analytics | PostHog | События главного сценария (см. launch-and-iterate.md), не pageviews |
| Logging | pino/structured stdout | Платформа (Vercel/Railway) соберёт; в каждой записи request_id и org_id |
| Hosting | Vercel / Railway / Fly | Превью-окружения обязательны |
| Домен + DNS | Cloudflare | И почтовый поддомен для рассылок |
| Backups | Автобэкапы Supabase/Neon | Проверь restore один раз руками до запуска |

## 5. Как фиксировать решения

Заведи в репо `docs/stack.md` на 10–15 строк: выбранный стек, схема core-таблиц (можно текстом), что осознанно отложено ("очередей нет — cron достаточно", "тёмной темы нет"). Каждый раз, когда пользователь предлагает добавить технологию, сначала спроси "какая боль прямо сейчас это требует?" — нет боли, нет технологии.
