# MVP Checklist — must-have vs nice-to-have, порядок реализации, что откладывать

Материалы этапов 2 (scoping) и 5 (build). Главное правило: MVP — это минимальный продукт, который выполняет Core Job от начала до конца и за который можно взять деньги. Всё остальное — после запуска.

## 1. Must-have vs nice-to-have

### Must-have (без этого не запускаемся)

**Продукт:**
- [ ] Один главный сценарий (Core Job) проходится от регистрации до ценности без участия разработчика
- [ ] Онбординг доводит нового пользователя до первого ценного результата ≤ 10 минут (в идеале ≤ 3)
- [ ] Пустые состояния главных экранов объясняют, что делать ("Создайте первый проект", не белый экран)
- [ ] Базовая мобильная адаптивность — сценарий проходится на телефоне; планка совместимости: текущий Chrome + мобильный Safari, не больше
- [ ] Способ оставить фидбек внутри продукта (кнопка/виджет или хотя бы mailto) и способ связаться с пользователем

**Инфраструктура:**
- [ ] Auth: email + Google OAuth; reset пароля работает
- [ ] Payments: Stripe Checkout, хотя бы один платный план; webhook выдаёт/забирает доступ идемпотентно
- [ ] Transactional email: welcome, reset пароля, чек об оплате; SPF/DKIM настроены
- [ ] Error tracking (Sentry) на фронте и сервере, алерты приходят
- [ ] Structured logging с request_id
- [ ] Analytics: события каждого шага главного сценария (signup → activation → payment)
- [ ] Бэкапы БД включены, restore проверен один раз руками

**Юридическое/гигиена:**
- [ ] Privacy Policy + Terms of Service (генератор + вычитка — достаточно для старта)
- [ ] Удаление аккаунта и данных (кнопка или явный email-процесс) — требование GDPR и маркетплейсов
- [ ] Страница цен с реальными ценами

### Nice-to-have (типовые кандидаты на "после запуска")

Тёмная тема; мобильное приложение; интеграции кроме одной критичной для Core Job; API для пользователей; команды/роли (если продукт B2C на старте — но см. multi-tenancy в tech-stack.md: схему БД под orgs закладывай сразу); дашборды и графики для пользователя; настройки профиля сверх минимума; несколько тарифов (достаточно одного платного); годовая оплата; локализация; admin-панель (первый месяц — SQL-консоль и Supabase Studio); email-маркетинг и drip-кампании; SSO/SAML; аудит-логи; экспорт данных в 5 форматах (один CSV — уже neat).

Правило спора: фича попадает в must-have, только если без неё Core Job не выполняется ИЛИ без неё нельзя законно взять деньги. "Пользователи привыкли, что в продуктах это есть" — не аргумент для MVP.

## 2. Порядок реализации (этап 5)

Строй в этой последовательности — каждый шаг оставляет систему в рабочем, деплоябельном состоянии:

1. **Скелет + деплой (день 1).** Репо, фреймворк, БД подключена, CI деплоит на прод-URL. Пустая страница на проде в первый день — обязательна: дальше каждый мердж виден живьём.
2. **Auth.** Регистрация, вход, Google OAuth. Схема users/organizations/memberships — сразу (см. tech-stack.md).
3. **Core-сущности + CRUD.** Таблицы главного сценария, создание/чтение/обновление. UI пока уродливый — нормально.
4. **Главный сценарий целиком.** Соедини шаги 2–3 в путь "новый пользователь → первый ценный результат". Прогони сам 10 раз. Это сердце MVP — сюда уходит основное время.
5. **Billing.** Stripe Checkout, один план, webhook, paywall на нужном месте сценария. Тест: карта 4242… → доступ открылся; отмена подписки → доступ закрылся.
6. **Transactional email.** Welcome, reset, receipt.
7. **Онбординг и полировка сценария.** Пустые состояния, подсказки первого запуска, сократи время до ценности.
8. **Гигиена перед запуском.** Sentry-алерты, analytics-события, бэкапы, ToS/Privacy, удаление аккаунта, страница цен.

Анти-паттерны порядка: неделя на настройку линтеров и монорепо (день 1 — это день 1, не неделя 1); billing "потом как-нибудь" (интеграция Stripe всплывает сюрпризами — делай в середине, не в ночь перед запуском); полировка UI до того, как сценарий работает целиком.

## 3. Scope creep — как удерживать

- Любая новая идея во время сборки записывается в `docs/after-launch.md` — и всё, к коду не приближается. Записать — не отказать, это снимает тревогу "забуду".
- Если пользователь настаивает на добавлении в scope, требуй размен: "ок, что вычёркиваем взамен, чтобы остаться в 6 неделях?"
- Раз в неделю сверяй факт с планом: если за неделю главный сценарий не продвинулся, а "мелочей" сделано много — это красный флаг, возвращай фокус на шаг 4.

## 4. Definition of Done для MVP

MVP готов к запуску, когда незнакомый человек из целевой персоны может сам, без твоей помощи:

1. Узнать о продукте (или получить инвайт) и зарегистрироваться.
2. Пройти Core Job до конца и получить результат.
3. Заплатить (если продукт платный) — и доступ откроется автоматически.
4. Вернуться через неделю — и его данные на месте, вход работает.
5. Сообщить тебе о проблеме, не разыскивая контакты.

Все пять — да? Запускайся. Не жди полировки: следующее знание придёт только от реальных пользователей.

## 5. Что можно отложить со спокойной душой

Частые страхи, которые НЕ нужны для запуска на 30–100 пользователей:

- **Масштабирование.** Один инстанс Vercel/Railway + Postgres free tier держат тысячи пользователей типового SaaS.
- **Идеальные тесты.** Достаточно: smoke-тест главного сценария (Playwright, 1 файл) + юнит-тесты на billing-логику. Покрытие ради покрытия — после PMF.
- **Красивый лендинг продукта.** Landing с этапа валидации + реальные скриншоты — достаточно.
- **Админка.** SQL и Supabase Studio первые месяцы.
- **Rate limiting и защита от абьюза** — базовый rate limit на auth-эндпоинты (Upstash/Vercel) — да; сложная антифрод-логика — после первого инцидента.
- **Оптимизация цен.** Одна цена, поднять никогда не поздно. Правило большого пальца — поставь цену, за которую неловко, и прибавь 20%.
